So funktioniert die Plattform

In der Hochschule gibt es viele kleine Aufgaben, die man mit einer kleinen Web-App lösen kann. Mit der Anwendungsplattform (AWP) bauen Fachabteilungen solche Mini-Apps selbst – mit Hilfe einer KI.

Kurz gesagt
  • Eine Mini-App löst genau einen Anwendungsfall und erscheint als Kachel im Portal.
  • Jede App startet aus derselben Vorlage. Darum sehen alle gleich aus und sind gleich sicher.
  • Die KI schreibt Code, Sie prüfen und geben frei.

Beispiele

  • Räume für Vormittag oder Nachmittag mit einem Klick reservieren.
  • Dienstreiseantrag in einer einfachen Oberfläche – die Belege liegen revisionssicher in ELO.
  • Dateien in bwSync&Share ansehen, hochladen, umbenennen, verschieben.

Der Weg in sieben Etappen

Wer macht was?

Am besten klappt es im Tandem: Eine Person kennt den fachlichen Ablauf sehr gut (z. B. wo in ELO welche Akte liegt). Eine zweite Person hat etwas technisches Verständnis (Git, Docker). Mehr unter Rollen & Support.

Nicht gedacht für

Große Anwendungen mit vielen Teilen. Dafür gibt es den klassischen Weg über die IT.

Die drei Umgebungen

Eine Umgebung ist ein Ort, an dem eine App läuft. Es gibt drei – jede mit eigenem Zweck und eigenen Daten.

Kurz gesagt
  • Lokal = ausprobieren. Test-VM = im echten Portal testen. Betrieb = für alle.
  • Lokal und auf der Test-VM nur Testdaten.

Was ist eine VM?

Eine VM (virtuelle Maschine) ist ein Rechner, der nur als Software auf einem echten Server läuft. Bei uns ist die Test-VM die Testumgebung auf einem Knoten im Hochschulnetz. Dort laufen Gateway, Portal und Ihre App genau wie später im Betrieb – aber nur mit Testdaten und ohne Internetzugang.

Hinweis

Diese Dokumentation behandelt Lokal und Test. Der Weg in den Betrieb wird gerade festgelegt.

Warum ein Adapter?

Die KI muss nicht wissen, wie Fachsysteme intern funktionieren. Und die Zugangsdaten liegen an einer geschützten Stelle – nicht in jeder App.

Golden Master

Ein Golden Master ist die fertige Vorlage (Template) für jede neue App – wie eine Briefvorlage in Word: Briefkopf, Schrift und Aufbau sind schon da, Sie schreiben nur den Inhalt.

Kurz gesagt
  • Jede App beginnt als Kopie einer Vorlage.
  • Es gibt zwei gleichwertige Vorlagen: Python (Standard) und JavaScript.
  • Sie ändern Manifest und App-Code – den Rest pflegt das Plattform-Team.

Dev Container

Ein Dev Container ist ein kleiner, abgeschlossener Computer in Ihrem Computer, in dem alle Werkzeuge schon installiert sind. Docker startet ihn, VS Code verbindet sich damit.

Kurz gesagt
  • Keine Programmiersprache und keine Werkzeuge selbst installieren – alles ist im Container.
  • Ihr Projektordner bleibt auf Ihrem Rechner – der Container „leiht“ ihn sich (Mount).
  • Kaputt? Rebuild Container – Projektdateien bleiben erhalten.

So hängt alles zusammen

Vorteile

Gleich für alle

Exakt dieselben Werkzeuge und Versionen. „Bei mir geht es aber“ gibt es nicht mehr.

Nichts installieren

Nur VS Code, Git und Docker auf dem eigenen Rechner.

Schnell neu aufsetzen

Container neu bauen – Projektdateien bleiben.

Passt zum Betrieb

Auch im Betrieb laufen Apps in Containern.

Host oder Container?

Wichtig für die Befehle: Manche laufen im Container (make dev, make check), andere auf Ihrem Rechner, dem Host (make docker), weil nur dort Docker verfügbar ist. make deploy führt nur die Freigabe-Verantwortliche aus. Siehe Befehle.

Was im Hintergrund passiert

Docker lädt ein Basis-Image von Microsoft mit Python 3.14, installiert uv und richtet mit uv sync --locked alle Pakete in den Versionen aus uv.lock ein. Erweiterungen: Python, Ruff.

Docker lädt ein Basis-Image von Microsoft mit Node.js 24 und richtet mit npm ci alle Pakete in den Versionen aus package-lock.json ein. Erweiterung: ESLint.

Die Konfiguration steht in .devcontainer/devcontainer.json.

Die KI: Claude Code und Skills

Claude Code ist ein KI-Assistent in VS Code. Sie beschreiben in normaler Sprache, was Ihre App tun soll – Claude Code schreibt den Code. Damit das Ergebnis zur Hochschule passt, arbeitet die KI nach festen Merkblättern: den Skills.

Kurz gesagt
  • Sieben Skills sagen der KI, wie eine App an der HKA aussehen und funktionieren muss.
  • Die KI sucht sich die passenden Skills selbst aus. Sie müssen keinen davon kennen.
  • Die KI schreibt Code – Sie prüfen, sichern und geben frei.
  • Die KI hat keinen Zugriff auf echte Daten, Passwörter oder Fachsysteme.

Was ist ein Skill?

Stellen Sie sich eine neue Kollegin vor, die sehr schnell schreibt, aber die Hochschule noch nicht kennt. Bevor sie anfängt, bekommt sie Merkblätter: „So sieht bei uns eine Seite aus“, „So gehen wir mit Passwörtern um“, „So schreiben wir Fehlermeldungen“. Genau das ist ein Skill – ein Merkblatt für die KI.

Die Skills liegen in jedem Projekt im Ordner .agents/skills/. Das Plattform-Team pflegt sie zentral. Sie lesen sie nicht und ändern sie nicht – aber es hilft zu wissen, was drinsteht.

So arbeitet die KI mit den Skills

  1. Sie

    Sie beschreiben Ihr Anliegen in eigenen Worten, zum Beispiel „Zeig meine Noten als Tabelle“.

  2. KI

    Sie vergleicht Ihre Worte mit dem Kopf jedes Skills und lädt nur die passenden – hier portal, schnittstellen und barrierefreiheit.

  3. KI

    Sie schreibt den Code nach diesen Regeln und hakt am Ende die Checkliste jedes Skills ab.

  4. Prüfung

    make check und die Pipeline prüfen automatisch, ob die Regeln eingehalten sind.

  5. Sie

    Sie schauen sich die Änderungen an, probieren die App aus und sichern den Stand.

Gut zu wissen

Sie müssen keinen Skill beim Namen nennen. Sprechen Sie so, wie Sie es einer Kollegin erklären würden. Die Beschreibungen der Skills sind bewusst mit Sätzen geschrieben, die Menschen wirklich sagen.

Git, Branches und Review

Git speichert jede Änderung – wie ein „Rückgängig-Knopf“ für das ganze Projekt. Das Projekt liegt als Repository auf GitHub.

Kurz gesagt
  • Sie arbeiten auf develop.
  • main ist geschützt – nur mit Review einer zweiten Person.

Warum Vier-Augen-Prinzip?

Eine App kann auf Daten in Fachsystemen zugreifen. Ein Fehler – aus Versehen oder absichtlich – könnte Daten löschen. Das Review schützt davor. Zusätzlich laufen bei jedem Pull Request automatische Prüfungen (Pipeline).

Anmeldung und Fachsysteme

Alle Apps nutzen dieselbe Anmeldung. Für manche Fachsysteme verbinden Sie zusätzlich Ihr eigenes Konto.

Kurz gesagt
  • Einmal anmelden – alle Apps kennen Sie und Ihre Rolle.
  • Zugangsdaten für Fachsysteme liegen verschlüsselt im Adapter und lassen sich jederzeit löschen.

Konto verbinden

  1. Sie

    „Konto verbinden“ in der App, beim Fachsystem anmelden.

  2. Adapter

    Speichert die Zugangsdaten verschlüsselt (SQLite). Verbindung über HTTPS.

  3. App

    Arbeitet über den Adapter in Ihrem Namen – nur mit Ihren Rechten.

  4. Sie

    „Konto trennen“ löscht die Zugangsdaten sofort.

Noch in Arbeit

Automatisches Löschen nach fester Frist (z. B. 7 Tage). Langfristig: zentrale Hochschul-Anmeldung (Shibboleth mit OIDC/SAML), Zugangsdaten nur für die Dauer der Sitzung.

Diesen Schritt führen Sie nicht selbst aus. Er gehört zur Freigabe. Hier steht, was dabei passiert.

Die fünf Schritte

Warum lokal bauen?

Die Test-VM hat aus Sicherheitsgründen keinen Internetzugang und kann keine Pakete nachladen. Darum kommt die App als fertiges Paket.

Weitere Optionen

  • Fertiges Image statt lokal bauen: make deploy VM=… IMAGE=ghcr.io/<owner>/<repo>@sha256:…
  • Lokaler Gesamtaufbau zum Testen: make deploy-local

Fehlercodes der Pipeline

Ist die Pipeline rot, steht in der Meldung ein Code wie PF-102. Hier sehen Sie, was er bedeutet und was Sie tun können.

Kurz gesagt
  • Eine rote Pipeline ist ein Hinweis, kein Hindernis. Fast immer können Sie den Fehler selbst beheben.
  • Fragen Sie im Zweifel Claude Code: „Die Pipeline ist rot und ich verstehe die Meldung nicht.“ Der Skill pipeline-fehler erklärt sie in einfachen Worten.

So sieht eine Meldung aus

Pipeline · Stufe secrets
============================================================
FEHLER PF-102 – Geheimnis im Code gefunden
Was ist passiert: In src/app/views.py (Zeile 12) steht etwas, das wie ein Schlüssel aussieht.
Warum wichtig: Wer den Code sieht, könnte damit arbeiten.
Was tun: Entfernen Sie den Schlüssel aus dem Code.
Er gilt als verbraucht – melden Sie ihn dem Plattform-Team.
Technische Details: (gekürzt, Werte geschwärzt)
============================================================

Jede Meldung folgt diesem Aufbau: Was ist passiert, Warum wichtig, Was tun. Die technischen Details brauchen Sie meist nicht.

Mehrere Container mit compose.yml

Standard ist ein Container. Braucht Ihre App mehr – z. B. eine kleine Datenbank – legen Sie compose.yml ins Repository.

Beispiel

services:
  app:
    build: .
    depends_on: [db]
  db:
    image: postgres:17-alpine
    environment: { POSTGRES_PASSWORD: nur-test } # nur Testdaten
    volumes: ["db-daten:/var/lib/postgresql/data"]
volumes:
  db-daten:

Regeln

  • Pflicht: ein Dienst namens app. Nur dieser ist für das Portal erreichbar.
  • Härtung für app setzt das Skript selbst.
Verboten

ports, privileged, network_mode, cap_add, Ordner vom Server (./ordner:…), eigene Netze, build außer bei app.

Häufige Fragen

Kurze Antworten auf Fragen, die oft gestellt werden.

Allgemein

Muss ich programmieren können?
Nein. Sie müssen Ihren fachlichen Ablauf gut beschreiben können. Etwas technisches Verständnis im Team (Git, Docker) hilft – am besten im Tandem.
Kann die KI meine echten Daten sehen?
Nein. Beim Schreiben von Code hat die KI keinen Zugriff auf Fachsysteme oder echte Daten.
Was ist der Unterschied zwischen Golden Master und meiner App?
Der Golden Master ist die Vorlage. Ihre App ist eine Kopie davon mit eigenem Inhalt.
Python oder JavaScript – was soll ich nehmen?
Im Zweifel Python, das ist der Standard. Beide Vorlagen können dasselbe, Ablauf und Regeln sind gleich. JavaScript lohnt sich, wenn Ihr Team damit schon arbeitet. Vergleich: Golden Master.
Warum brauche ich Docker?
Docker startet den Dev Container (Ihren fertigen Arbeitsplatz) und baut das Image für die Test-VM.
Kann ich meine App selbst ins Portal bringen?
Nein. Das entscheidet und erledigt die Freigabe-Verantwortliche. Sie schicken einen Antrag – siehe Freigabe beantragen.
Wie lange dauert eine eigene App?
Das hängt von der Idee ab. Die Anleitung ist in kurze Etappen geteilt, sodass Sie in mehreren kleinen Sitzungen arbeiten können. Je klarer der Ideen-Steckbrief, desto schneller geht es.
Kann ich ohne Hochschulnetz entwickeln?
Lokal ja – mit Test-Anmeldung und Testdaten. Zum Testen im Portal der Test-VM brauchen Sie VPN.
Was passiert mit meinen Daten, wenn die App gelöscht wird?
Das hängt davon ab, wo sie liegen. Siehe Wo Daten liegen dürfen.
